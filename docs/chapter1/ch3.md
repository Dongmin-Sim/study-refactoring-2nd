# 3장 코드에서 나는 악취

리팩터링이 어떻게 작동하는지 감이 왔을 것이다. 하지만 "작용 방법"을 아는 것과 "제때 적용"할 줄 아는 것은 다르다. 
리팩터링을 언제 시작하고 언제 그만할지를 판단하는 일은 리팩터링의 작동 원리를 아는 것 못지않게 중요하다.

"언제"해야 하는지에 대해서는 명확하게 정립된 규칙이 없다. 리팩터링 초판을 집필하면서 이 주제로 켄트 백을 만나러 갔는데 갓 태어난 딸을 돌보느라 
기저귀 냄새에 상당히 민감했다고 함. 그 때문인지 리팩터링할 '시점'을 설명하는데 '냄새'란 표현을 사용했다고 함. 

> 악취라는 표현이 여기서 비롯된거였다니 

켄트 벡와 마틴 파울러는 수많은 프로젝트들을 수행하면서, 리팩토링이 필요한, 아주 절실한 코드들에 일정한 패턴이 있다는 사실을 발견했다고 함. 

하지만 리팩터링을 언제 멈춰야 하는지를 판단하는 정확한 기준을 제시하지 않을 것. 종료 기준보다는 리팩터링하면 해결할 수 있는 문제의 징후를 제시해준다고 함.

인스턴스, 메서드 줄 수 같은 것들은 각자 경험을 통해 감을 키워야 함. 

먼저 악취가 무엇인지 찾고, 해법으로 제시한 리팩터링 기법을 찾아 읽고, 냄새를 없애는 데 도움이 될지 생각해본다. 완전히 똑같지 않더라도 힌트가 되어줄지도 모른다.

## 기이한 이름 Mysterious Name

코드를 명료하게 표현하는 데 가장 중요한 요소 하나는 바로 '이름'이다. 그래서 함수, 모듈, 변수, 클래스 등은 그 이름만 보고도 각각이 
무슨 일을 하고 어떻게 사용해야 하는지 명확히 알 수 있도록 엄청나게 신경 써서 이름을 지어야 한다.

아쉽게도 이름 짓기는 프로그래밍에서 가장 어렵기로 손꼽히는 2가지 중 하나다. 
- 함수 선언 바꾸기 
- 변수 이름 바꾸기 
- 필드 이름 바꾸기

처럼 이름을 바꾸는 리팩터링들이다. 이름만 잘지어도 나중에 문맥을 파악하느라 해매는 시간을 크게 절약할 수 있다.

**마땅한 이름이 떠오르지 않는다면 설계에 더 근본적인 문제가 숨어 있을 가능성이 높다.** 그래서 혼란스런 이름을 잘 정리하다 보면 코드가 훨씬 간결해질 때가 많다.

## 중복 코드 Duplicated Code
똑같은 코드 구조가 여러 곳에서 반복된다면 하나로 통합할 수 있다.

코드가 중복되면 각각을 볼 때마다 서로 차이점은 없는지 주의 깊게 살펴봐야 하는 부담이 생긴다. 

가장 간단한 중복 코드의 예로, 한 클래스에 딸리 두 메서드가 똑같은 표현식을 사용하는 경우가 있다.
```java
public class DuplicateCodeExample {

    // 두 메서드에서 동일한 표현식을 사용한 예시
    public int calculateSquare(int number) {
        return number * number; // 동일한 표현식
    }

    public int calculateDoubleSquare(int number) {
        return (number * number) * 2; // 동일한 표현식 포함
    }
}
```
이럴때, `함수 추출하기`로 다음과 같이 중복을 제거할 수 있다.
```java
public class DuplicateCodeExample {

    // 함수 추출하기
    private int square(int number) {
        return number * number;
    }

    public int calculateSquare(int number) {
        return square(number);
    }

    public int calculateDoubleSquare(int number) {
        return square(number) * 2;
    }
}
```
완전히 똑같지는 않고 비슷한 코드가 존재한다면, `문장 슬라이스`로 비슷한 부분을 한 곳에 모아 함수 추출하기를 더 쉽게 적용할 수 있는지 살펴본다. 

같은 부모로부터 파생된 서브 클래스들에 코드가 중복되어 있다면 각자 따로 호출하지 않고 `메서드 올리기`를 적용해 상위 클래스로 옮긴다. (상속 효과 극대화)
