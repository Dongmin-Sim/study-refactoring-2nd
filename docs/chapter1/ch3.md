# 3장 코드에서 나는 악취

리팩터링이 어떻게 작동하는지 감이 왔을 것이다. 하지만 "작용 방법"을 아는 것과 "제때 적용"할 줄 아는 것은 다르다. 
리팩터링을 언제 시작하고 언제 그만할지를 판단하는 일은 리팩터링의 작동 원리를 아는 것 못지않게 중요하다.

"언제"해야 하는지에 대해서는 명확하게 정립된 규칙이 없다. 리팩터링 초판을 집필하면서 이 주제로 켄트 백을 만나러 갔는데 갓 태어난 딸을 돌보느라 
기저귀 냄새에 상당히 민감했다고 함. 그 때문인지 리팩터링할 '시점'을 설명하는데 '냄새'란 표현을 사용했다고 함. 

> 악취라는 표현이 여기서 비롯된거였다니 

켄트 벡와 마틴 파울러는 수많은 프로젝트들을 수행하면서, 리팩토링이 필요한, 아주 절실한 코드들에 일정한 패턴이 있다는 사실을 발견했다고 함. 

하지만 리팩터링을 언제 멈춰야 하는지를 판단하는 정확한 기준을 제시하지 않을 것. 종료 기준보다는 리팩터링하면 해결할 수 있는 문제의 징후를 제시해준다고 함.

인스턴스, 메서드 줄 수 같은 것들은 각자 경험을 통해 감을 키워야 함. 

먼저 악취가 무엇인지 찾고, 해법으로 제시한 리팩터링 기법을 찾아 읽고, 냄새를 없애는 데 도움이 될지 생각해본다. 완전히 똑같지 않더라도 힌트가 되어줄지도 모른다.

## 기이한 이름 Mysterious Name

코드를 명료하게 표현하는 데 가장 중요한 요소 하나는 바로 '이름'이다. 그래서 함수, 모듈, 변수, 클래스 등은 그 이름만 보고도 각각이 
무슨 일을 하고 어떻게 사용해야 하는지 명확히 알 수 있도록 엄청나게 신경 써서 이름을 지어야 한다.

아쉽게도 이름 짓기는 프로그래밍에서 가장 어렵기로 손꼽히는 2가지 중 하나다. 
- 함수 선언 바꾸기 
- 변수 이름 바꾸기 
- 필드 이름 바꾸기

처럼 이름을 바꾸는 리팩터링들이다. 이름만 잘지어도 나중에 문맥을 파악하느라 해매는 시간을 크게 절약할 수 있다.

**마땅한 이름이 떠오르지 않는다면 설계에 더 근본적인 문제가 숨어 있을 가능성이 높다.** 그래서 혼란스런 이름을 잘 정리하다 보면 코드가 훨씬 간결해질 때가 많다.

## 중복 코드 Duplicated Code
똑같은 코드 구조가 여러 곳에서 반복된다면 하나로 통합할 수 있다.

코드가 중복되면 각각을 볼 때마다 서로 차이점은 없는지 주의 깊게 살펴봐야 하는 부담이 생긴다. 

가장 간단한 중복 코드의 예로, 한 클래스에 딸리 두 메서드가 똑같은 표현식을 사용하는 경우가 있다.
```java
public class DuplicateCodeExample {

    // 두 메서드에서 동일한 표현식을 사용한 예시
    public int calculateSquare(int number) {
        return number * number; // 동일한 표현식
    }

    public int calculateDoubleSquare(int number) {
        return (number * number) * 2; // 동일한 표현식 포함
    }
}
```
이럴때, `함수 추출하기`로 다음과 같이 중복을 제거할 수 있다.
```java
public class DuplicateCodeExample {

    // 함수 추출하기
    private int square(int number) {
        return number * number;
    }

    public int calculateSquare(int number) {
        return square(number);
    }

    public int calculateDoubleSquare(int number) {
        return square(number) * 2;
    }
}
```
완전히 똑같지는 않고 비슷한 코드가 존재한다면, `문장 슬라이스`로 비슷한 부분을 한 곳에 모아 함수 추출하기를 더 쉽게 적용할 수 있는지 살펴본다. 

같은 부모로부터 파생된 서브 클래스들에 코드가 중복되어 있다면 각자 따로 호출하지 않고 `메서드 올리기`를 적용해 상위 클래스로 옮긴다. (상속 효과 극대화)

## 긴 함수 Long Function
오랜 기간 잘 활용되는 프로그램들은 하나같이 짧은 함수로 구성됐음.  
짧은 함수들로 구성된 코드 베이스를 얼핏 훑으면 연산하는 부분이 하나도 없어 보임. 왜냐하면 코드가 끝없이 위임하는 방식으로 작성되어 있기 때문. 

간접 호출의 효과, 즉 코드를 이해하고 공유하고 선택하기 쉬워진다는 장점은 함수를 짤게 구성할 때 나온다. 

이전에는 서브 루틴을 호출하는 비용이 컸었어서 짧은 함수를 꺼려했지만, 요즘에는 프로세스 안에서 함수 호출 비용이 거의 없어졌음.  
코드를 읽는 사람의 입장에서는 이해하기 위해서 함수를 왔다갔다 것때문에 부담이 존재함.  

그렇기 때문에 짧은 함수로 구성된 코드를 이해하기 쉽게 만드는 가장 확실한 방법은 좋은 이름이다. 함수 이름을 잘 지어두면 본문 코드를 볼 이유가 사라진다.  
그렇게 하기 위해서는 훨씬 적극적으로 함수를 쪼개야 한다. 
- 주석을 달아야 할 만한 부분은 무조건 함수로 만든다. 
- 함수 본문에는 주석으로 설명하려던 코드가 담기고
- 함수 이릉은 동작 방식이 아닌 '의도'가 드러나게 짓는다. 

핵심은 함수의 길이가 아닌, 함수의 목적(의도)과 구현 코드의 괴리가 얼마나 큰가이다.   
즉, '무엇을 하는지'를 코드가 잘 설명해주지 못할수록 함수로 만드는게 유리하다.

함수로 짧게 만드는 작업의 99%로는 **함수 추출하기**  함수 본문에서 따로 묶어 빼내면 좋을 것 같은 코드 덩어리를 찾아 새로운 함수로 만든다.  

함수가 매개변수와 임시변수를 많이 사용한다면 추출 작업이 어려워진다.(추출한 함수에도 매개변수가 많아짐. -> 리팩터링 후에도 더 난해해짐)
- **임시변수를 질의 변수로 바꿔서** 임시 변수의 수를 줄이고, 
- **매개변수 객체 만들기**와 **객체 통째로 넘기기**를 사용해 배개면수의 수를 줄여볼 수 있다.

여전히 임시변수와 매개변수가 많다면, **함수를 명령으로 바꾸기**를 고려해본다.

### (함수로) 추출할 코드 덩어리 찾기
주석을 참고하는 것. 주석은 코드만으로는 목적을 이해하기 어려운 부분에 달려 있는 경우가 많다. 이런 주석을 찾으면, 주석이 설명하는 코드와 함께 함수로 빼내고, 
함수 이름은 주석 내용을 토대로 지을 수 있다. 

- 코드가 단 한줄이라도 설명할 필요가 있다면 함수로 추출하는게 좋음.

### 조건문과 반복문도 추출 대상이 될 수 있다. 
조건문과 반복문도 추출 대상의 실마리를 제공한다. 
- 조건문은 **조건문 분해하기** 를 사용. 
  - 거대한 switch 문은 case문 마다 함수 추출하기로 바꿔서 `case본문:함수호출문` 으로 대응시킬 수 있다.
  - 같은 조건을 기준으로 나뉘는 switch 문이 여러개라면 **조건부 로직을 다형성으로 바꾸기**를 적용
- 반복문도 그 안의 코드와 함께 추출해 독립된 함수로 만든다. 
  - 추출한 반복문 코드를 대표하는 함수명이 떠오르지 않는다면 여러 작업이 섞여있을 가능성이 높음. -> **반복문 쪼개기**를 시도해본다.

## 긴 매개변수 목록 Long Parameter List
이전에는 함수에 필요한 것들을 모조리 매개 변수로 전달하는 것이 관례였음. 그래야 전역 데이터가 늘어나는 것을 막을 수 있기 때문.

이때 고려해볼 수 있는 action item 들은 다음과 같음.
- 종종 다른 매개변수에서 값을 얻어올 수 있는 매개변수가 있는데, 이런 매개변수는 **매개변수를 질의 함수로 바꾸기**로 제거할 수 있다.
- 사용중인 데이터 구조에서 값들을 각각 뽑아 별개의 매개변수로 전달하는 코드라면 **객체 통째로 넘기기**를 고려 
- 항상 함께 전달되는 매개변수들은 **매개변수 객체 만들기**로 하나로 묶어버리기
  - 매개변수들 중 연관성이 높은 매개변수가 있는지 찾아보기
- 함수의 동작 방식을 정하는 플래그 역할의 매개변수는 **플래그 인수 제거하기**로 없애주기
- 클래스를 통해서 매개변수 목록을 줄일 수 있다. (특히 여러 개의 함수가 특정 매개변수들의 값을 공통으로 사용할 때)
  - 이럴 때는 **여러 함수를 클래스로 묶고** 이 함수들이 사용하는 공통 값들을 클래스 멤버 변수로 정의한다.


## 3.5 전역 데이터 Global Data
전역 데이터는 코드베이스 어디서든 건드릴 수 있고, 값을 누가 바꿨는지 찾아낼 매커니즘이 없다는게 문제.
전역 데이터의 대표적인 형태는 전역변수, 클래스변수 싱글톤에서도 같은 문제가 발생함. 

🤔 이를 위해 고민해볼 리팩터링 
1. `변수 캡슐화하기`
  - 데이터를 함수로 감싼다. 
  - 접근자 함수들을 클래스나 모듈에 넣고 접근 범위를 최소로 줄인다.

## 3.6 가변 데이터 Mutable Data
코드의 다른 곳ㅇ서는 다른 값을 기대한다는 사실을 인식하지 못한 채 데이터를 변경해버리면 프로그램이 오작동한다. 
아주 드문 조건에서만 발생한다면 원인 찾기가 어려움.

🤔 이를 위해 고민해볼 리팩터링
1. `변수 캡슐화하기`
  - 함수를 거쳐가도록 감싸기(데이터를 변경으로부터 감시)
2. `변수 쪼개기`
   - 하나의 변수에 용도가 다른 값들을 저장하기 위해 수정하는 경우
3. `문장 슬라이드하기`, `함수 추출하기`
   - 무언가를 갱신하는 코드로부터 부작용이 없는 코드를 분리. 
4. `질의함수와 변경함수 분리하기` + `세터 제거하기`
   - 꼭 필요한 경우가 아니라면 부작용이 있는 코드를 호출할 수 없게함.
   - 세터를 호출하는 클라이언트를 찾는 것만으로도 변수의 유효범위를 줄이는데 도움될 때가 있음.
5. `파생 변수를 질의 함수로 바꾸기`
   - 값을 다른 곳에서 설정할 수 있는 가변 데이터가 있는 경우.
6. `여러 함수를 클래스로 묶기`, `여러 함수를 변환함수로 묶기`
   - 유효범위가 넓다면, 변수를 갱신하는 코드들의 유효범위를 제한할 수 있다.
7. `참조를 값으로 바꾸기`
   - 구조체를 통째로 교체해버리기

## 3.7 뒤엉킨 변경 Divergent Change
뒤엉킨 변경은 단일 책임 원칙이 제대로 지켜지지 않을 때 나타난다. 
즉, 하나의 모듈이 서로 다른 이유들로 인해 여러 가지 방식으로 변경되는 일이 많을 때 발생한다.

뒤엉킨 변경의 예시로, 데이터베이스가 추가될 때마다 함수 3개를 바꾸고, 
금융상품이 추가될 때마다 또 다른 함수 4개를 바꿔야하는 모듈이 있다면 뒤엉킨 변경이 발생했다는 뜻이다.

🤔 이를 위해 고민해볼 리팩터링
1. `단계 쪼개기`
   - 일의 순차적으로 실행된다면, 다음 맥락에 필요한 데이터를 특정한 데이터 구조에 담아 전달하는 식으로 분리(DTO?)
2. `함수 옮기기` + `함수/클래스 추출하기`
   - 전체 과정 속, 각기 다른 맥락의 함수를 호출하는 빈도가 높다면, 각 맥락의 모듈들을 만들어 관련 함수들을 모은다.
   - 그러면 처리 과정이 맥락별로 구분됨.
   - 여러 맥락의 일에 관여하는 함수가 있다면 옮기기 전에 추출부터.
